# Service reliability

The service catalog is workspace-scoped. Owners and administrators manage bounded service records, active-member ownership, project links, dependencies, SLOs and synthetic monitors. Members have read access. Dependencies are unique, cannot point to the same service, and are checked through a traversal limited to 10 levels and 500 nodes before insertion. Impact responses are tabular and bounded.

SLO definitions allow availability, error-rate and latency indicators with 7, 28, 30 or 90-day windows. Editing creates an immutable version and archives the prior version. Samples bind to the active SLO version, use a workspace-scoped idempotency key, accept batches of at most 100, reject timestamps over five minutes ahead or seven days old, and expire after 400 days. Metadata is limited to 20 short keys. Missing data is `unknown`, `bad`, or explicitly skipped according to the definition; it never silently becomes healthy.

Compliance is `good / total`. The allowed bad fraction is `1 - target`; budget consumption is the observed bad fraction divided by that allowance, and remaining budget is `max(0, 1 - consumption)`. Empty windows are unknown unless the configured policy treats missing data as bad. Evaluations store the SLO version and bounded window so later edits do not rewrite history. Metrics exclude unknown data from healthy totals.

Synthetic monitoring supports GET and HEAD over HTTPS port 443. URLs reject credentials, private, loopback, link-local, multicast, reserved, metadata and internal destinations across IPv4 and IPv6. DNS answers are checked before every request and the connection is pinned to an approved address. Every redirect is revalidated; redirect count, response bytes, header size, timeout and assertions are bounded. Secret headers use the existing authenticated, versioned encryption and are write-only. Full response bodies, headers, resolved addresses and stack traces are never persisted.

The existing automation worker claims due monitors with expiring leases. A stable monitor/schedule hash prevents overlapping duplicate history. It rechecks enabled and archived state after claiming, records sanitized results, retries infrastructure failures after a bounded delay, and distinguishes endpoint health from infrastructure failure. Run one or more existing automation workers against the same replica-set database and encryption keyring; this release makes no multi-region claim.

Authenticated APIs are rooted at `/api/workspaces/:workspaceId/reliability`. Lists and histories use bounded pages. Ingestion is available at `POST .../sli`; callers need an active workspace membership. Public status APIs never expose service IDs or catalog metadata. Linking a status component is metadata only and does not publish incidents or change public health.

Production requires the existing MongoDB replica set, Redis coordination, automation worker, and encryption keys. Rotate secret encryption keys by adding the new key and changing `AUTOMATION_KEY_VERSION`; retain older keys until monitor secrets are rewritten. Retention, insufficient data, and synthetic exclusions must be considered when comparing reliability metrics.
